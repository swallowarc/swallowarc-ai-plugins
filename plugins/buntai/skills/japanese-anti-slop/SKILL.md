# 日本語 AI 臭除去の規範

LLM が生成する日本語には、内容と独立に繰り返される定型のパターンがある。
本規範はそのパターンを除去し、書き手の声を保ったまま、文章を読み手のための品質に引き上げる。
目的は読み手にとっての品質であり、AI 検出器のスコアを下げることは目的にしない。

## 三つの使い方

- **Edit（既定）**: 草稿を受け取って直す。パターンを除去した全文と、変更点の短い報告を返す。
- **Detect**: 「AI 臭くないか見て」「指摘だけして」と言われたとき。書き直さず、パターン名・原文引用・修正案の一覧を返す。「AI が書いたかどうか」の判定はしない。検出器の判定は当て推量であり、個別のパターン指摘だけが読者に検証可能な証拠である。
- **執筆時併用**: 新規に文章を生成するとき。最初の一文からパターンを避けて書き、書き上げたら同一ターン内で「機械的点検手順」を実施してから納品する。執筆規範スキル（`buntai:japanese-tech-writing` など）と併用する場合、執筆はそちらの規範が、点検は本スキルが担う。

## 編集原則

- 最小限の有効な編集にとどめる。パターンに該当しない文は触らない。人間らしい強い文はそのまま残す。
- 編集の前に草稿の声（語彙の硬さ、リズム、断定の強さ、ユーモア、脱線）を把握し、編集後も同じ書き手の文章に読めることを目標にする。書き手の過去の文章サンプルが与えられたら、本スキルの文体既定よりサンプルの癖を優先する。
- 意味を変えない。事実・主張・数値・固有名詞は、追加も削除も誤りとして扱う。具体性を上げるために事実を捏造しない。足りない具体は書き手に尋ねる。

## パターンカタログ

各パターンは「警戒表現 → 問題 → 処置」の形で示す。Before/After は例であり、字面の置換表ではない。

### 内容のパターン

**1. 意義の水増し**
警戒表現: 「重要な一歩」「大きな転換点」「〜を象徴する」「〜の礎」「進化し続ける」「〜の在り方を変える」「新時代の」
ふつうの事実に歴史的意義や潮流を後付けする。
Before: 「2019 年の v2 リリースは、プロジェクトの歴史における重要な転換点であり、モダンなフロントエンド開発の進化を象徴しています。」
After: 「2019 年の v2 でプラグイン API が導入され、外部の開発者が機能を追加できるようになった。」

**2. 営業・宣伝口調**
警戒表現: 「魅力的な」「強力な」「豊富な」「充実した」「〜に最適」「注目を集めている」「必見」
説明のはずの文章が広告になる。
Before: 「直感的な UI と豊富な機能を兼ね備えた、開発者必見の強力なツールです。」
After: 「ログの検索と可視化ができる。インストールから最初のグラフ表示まで 5 分かからなかった。」

**3. 曖昧な出典**
警戒表現: 「専門家によると」「〜と言われています」「〜とされています」「一般に〜と考えられています」「多くの開発者が」
主張を誰のものでもない権威に預ける。出典を名指しできるなら名指しする。できないなら、自分の判断として書き直すか、主張ごと削る。出典を捏造しない。

**4. 浅い意味づけ**
事実の後ろに連用形で解釈をぶら下げ、深みを装う。英語 AI 文の -ing 句分析（"..., highlighting its commitment to..."）の日本語形。
Before: 「同社は週次で勉強会を開催しており、技術への強いコミットメントを示しています。」
After: 「同社は週次で勉強会を開催している。」
解釈が本当に必要なら、根拠を伴う独立した文として書く。

**5. 形式的な「課題と展望」**
警戒表現: 「一方で課題も残されています」「これらの課題を乗り越えた先に」「今後のさらなる発展が期待されます」
中身のない課題節・展望節を反射的に付ける。特定の課題と現在の対応だけを書き、書けることがなければ節ごと削る。

### 語彙と文法のパターン

**6. ピボット構文の乱用**
警戒表現: 「〜ではなく〜」「単なる〜ではない」「〜だけでなく〜も」
誰も主張していない X を立てて否定し、Y を持ち上げる。1 回は修辞、連発は癖である。
Before: 「これは単なるエディタではありません。開発体験そのものを変えるプラットフォームなのです。」
After: 「このエディタは LSP と拡張 API を持ち、ビルドとデバッグも同じ画面で完結する。」
実際にありそうな誤解を根拠つきで訂正する否定は残す。

**7. 三点セット強迫**
内容が 2 つでも 4 つでも、3 つに整えて完結感を出す。
Before: 「導入により、開発速度、コード品質、チームの士気が向上します。」
After: 「導入後、レビューの往復が減り、マージまでの時間は平均 2 日から半日になった。」
実際の数に合わせる。並列をやめて 1 項目を具体化する手もある。

**8. 冗長な言い回し**
- 「〜することができます」「〜することが可能です」→「〜できます」
- 「検討を行う」「実装を行う」（サ変名詞＋を行う）→「検討する」「実装する」
- 「〜という形で」→ 削るか「〜として」
- 「〜においては」→「〜では」
- 「〜に関して」「〜について」の乱用 → 助詞で直接つなぐ
- 「〜する必要があります」の連発 → 理由を添えて言い切るか、文型を変える

**9. 頻出 AI 語彙の密集**
警戒表現: 「活用する」「実現する」「提供する」「〜性を高める」「向上させる」「鍵となる」「本質的な」「包括的な」「多角的な」「様々な」「まさに」「非常に」「極めて」「大幅に」「飛躍的に」「シームレスな」「柔軟な」「堅牢な」
どれも単発では無罪である。1 段落に複数密集したら、どの文も具体的な情報を運んでいない徴候と見なす。動詞は動作の中身に、形容は測れる事実に置換する。
Before: 「本ツールを活用することで、柔軟かつ堅牢なデータ連携を実現し、業務効率を大幅に向上させることができます。」
After: 「本ツールは CSV と API の両方からデータを取り込める。取り込みに失敗した行は行単位でリトライされる。」

**10. 同義語ローテーション**
同じ対象を「本ツール」「このソフトウェア」「当該プロダクト」と言い換えて回す。呼び名を 1 つ決めて通す。繰り返しが気になるときは、代名詞か主語の省略（日本語では自然）で受ける。

**11. 主語のない受動態・自発**
警戒表現: 「〜が期待されます」「〜が求められています」「〜と考えられます」「〜が推奨されます」
誰の期待・要求・推奨なのかを隠す。
Before: 「テストの自動化が求められています。」
After: 「リリース前の手動テストに毎回 2 日かかっている。回帰テストを自動化したい。」
学術論文や報告書など、行為者が自明で受動態が慣例のレジスタでは残してよい。

**12. 文末の単調**
- 同形の文末（「〜ます。」「〜です。」「〜である。」）が 3 文以上続いたら、体言止め・疑問・「〜だろう」・倒置のどれかで 1 か所崩す。崩しすぎはパターン 17 の症状になる。
- 「〜と言えるでしょう」「〜ではないでしょうか」は、本当に読者に問うている場合を除き断定に直す。
- ですます調とである調を 1 つの文章で混ぜない（引用・会話文・箇条書き内の体言止めは例外）。

### 文体と整形のパターン

**13. 太字の乱発**
強調が多いことは、強調がないことと同じである。1 節に 1〜2 箇所まで。誤読を防ぐ否定や結論に限り、それ以外は語順と文構造で際立たせる。

**14. 絵文字の装飾**
見出しや箇条書きの頭の絵文字（🚀 ✅ 💡）は削る。本文の絵文字は、チャットのレジスタで書き手自身が使う場合に限る。

**15. 「ラベル：説明」型箇条書きの乱発**
すべての情報を「**見出し語**：一文」のリストに整形する癖。項目間の論理関係（因果、対比、順序）が失われる。
Before:
「- **高速性**: 従来比 3 倍の処理速度を実現します。
 - **安全性**: 型チェックにより実行前にエラーを検出します。」
After: 「型チェックを実行前に済ませるため実行時の検査が減り、従来の約 3 倍の速度で処理できる。」
項目間に関係があるなら地の文へ。定義・手順・選択肢のような本当の列挙はリストのままでよい。

**16. 見出しの復唱**
見出しの直後に、見出しを言い直しただけの一文を置かない。最初の文から中身に入る。

**17. 短文断定・体言止めの連打**
Before: 「結果は明白。速度は 3 倍。もう戻れない。」
After: 「移行後、ビルドは 90 秒から 30 秒になった。元の構成に戻す理由は今のところない。」
短文の強調は 1 か所なら効くが、連打はリズムの演出で内容の不足を隠す。読み物としての緩急を設計したいときは `buntai:cognitive-rhythm-writing` の規範に従う。

**18. アフォリズム風の締め**
警戒表現: 段落や記事の最後に置かれた、引用されそうな決め台詞（「キャッシュとは、過去の自分から未来の自分への贈り物なのです。」）。
決め台詞は削除する。より上手い比喩に書き換えるのは処置ではない。最後の段落は、具体的な事実、未解決の論点、次の行動のどれかで終える。

**19. メタな前置き**
警戒表現: 「重要なのは」「ここで注目すべきは」「見落とされがちですが」「〜について見ていきましょう」
前置きを削って主張をそのまま書く。「結論から言うと」は、直後に本当に結論が来るなら残してよい。

### チャット痕跡のパターン

**20. チャット応対の混入**
警戒表現: 「以下に〜をまとめました」「もちろんです」「承知しました」「ご質問があればお知らせください」「お役に立てれば幸いです」
チャットの応対文が、単独で読まれる文章に残っている。発見次第削除する。

**21. 記事の常套句**
警戒表現: 「いかがでしたか」「参考になれば幸いです」「ぜひ試してみてください」「今後の動向に注目です」
締めの定型句を削り、最後の実質的な文で終える。

**22. 中身のない「まとめ」**
直前の内容の言い換えだけの「まとめ」節は削る。長い文章で再確認が本当に必要な場合に限り、適用条件や限界など新しい観点を 1 つ添えて短く書く。

**23. 過剰な同意**
警戒表現: 「素晴らしい質問です」「おっしゃる通りです」「良い視点ですね」
削除する。同意するなら、相手の主張のどこが正しいかを特定して述べる。

**24. 知識の断り書き**
警戒表現: 「私の知識の範囲では」「最新の情報については公式サイトをご確認ください」の反射的な付加。
知っていることを書き、知らないことは「〜は確認していない」と特定して書く。バージョン依存の記述など、時点の限定が内容に必要な場合は残す。

## 誤検出ガード

次のものは、単独では AI の証拠にならない。

- 整った文法・丁寧な構成。推敲された人間の文章も整っている。
- ですます調そのもの。
- 箇条書き・太字・見出しの存在。乱発だけが徴候である。
- 「しかし」「また」「一方で」などの接続詞の単発使用。
- 単発の三並列、単発の体言止め、単発の「〜ではなく」。密集・連打したときだけ徴候になる。

判定は常に複数パターンの重なりで行う。1 つの表現だけを根拠に「AI っぽい」と指摘しない。

次のものは書き換えの対象にしない。

- 引用文・会話文・原文の再掲。
- 固有名詞・製品名・定着した術語。名称の一部に警戒表現が含まれていても触らない（「データ活用基盤」など）。
- パターンそのものを説明・言及している語句。

## 残すべき人間らしさ

以下は書き手の声である。パターンに似ていても保持する。

- 迷い・両価的な感情: 「便利だとは思う。ただ、どこか腑に落ちない。」
- 一般化できない具体: 固有の場所・人・時刻を伴う、その人にしか書けないディテール。
- 自己訂正・脱線: 「（『ほぼ毎回』と書きかけたが、記録を見返すと毎回だった）」
- 書き手の癖: あえての反復、口癖、くだけた表現。文章内で一貫していれば統一しない。
- 強い意見・ユーモア・毒。安全で無難な表現に丸めない。

削るかどうか迷ったら、「この表現は誰が書いても同じか、この書き手だから書いたのか」を問う。後者なら残す。

## 機械的点検手順

Edit と執筆時併用では、書き上げた本文に対して以下を実施する。
「読み返した感じ問題ない」は点検未実施と同じである。自分が直前に書いた文章への感覚的な検査は、書いた本人であるがゆえに必ず甘くなる。数えた結果だけを信用する。

1. **表現の走査**: 次の各表現を本文から実際に検索し、出現回数を明記する（ゼロも「0」と書く）。
   「することができ」「することが可能」「を行う」「と言えるでしょう」「ではないでしょうか」「非常に」「極めて」「まさに」「とされています」「と言われています」「だけでなく」「ではなく」「様々な・さまざまな」「実現」「活用」
   回数が多い項目から、文脈を見て置換または削除する。
2. **整形の計数**: 太字の箇所数、絵文字の数、「ラベル：説明」型リストの数を数える。
3. **文末の点検**: 各文の文末を順に書き出し、同形が 3 連続する箇所を探して 1 か所崩す。
4. **三並列の点検**: 3 項の並列をすべて挙げ、それぞれ「本当に 3 つあるのか」を確認する。
5. **段落末の点検**: 各段落の最後の文を見て、アフォリズム風の締め（18）と浅い意味づけ（4）がないか確認する。
6. **再走査**: 修正のために書き直した文は、最初の草稿と同じ確率で同じ臭いを再導入する。修正箇所だけもう一度 1〜5 にかける。

Detect では、この手順の結果（出現回数）を指摘の裏付けとして提示する。

## レジスタ別の調整

- **技術書・技術記事**: 執筆規範は `buntai:japanese-tech-writing` が優先。本スキルは書き上げ後の点検として使う。両者の指示が重なる場合（箇条書きの扱いなど）はあちらに従う。
- **ビジネスメール・社外文書**: 「お世話になっております」「よろしくお願いいたします」などの定型の挨拶は礼儀であって AI 臭ではない。削らない。削るのは本文の水増し（20・21・24）である。
- **ブログ・エッセイ**: 声の保持を最優先する。規範的な整いより書き手の個性が価値を持つ。最小限の編集にとどめる。
- **チャット・Slack**: 完全な文である必要はない。むしろ、全文が整った敬体で構造化されていることが最大の臭いになる。断片・省略・言い直しを許す。

## 出力形式

- **Edit**: 編集後の全文を出し、そのあとに変更点の短い報告（適用したパターン番号と代表例 2〜3 件）を添える。
- **Detect**: パターン番号と名前、原文の引用、短い修正案の 3 点を一覧で示す。評点や「AI が書いたか」の判定はしない。修正案の中でも事実を捏造しない。原文にない具体値（数値、サービス名、事例）が必要な修正案は、プレースホルダ（「◯◯」）か書き手への質問の形で示す。
- **他タスクからの利用**: 別の作業（コミットメッセージ、PR 説明、ドキュメント生成）の内部で本スキルを使う場合は、最終文のみを返す。
